## 指摘

### [R1-1][Medium][includes/Woo/Tools/PrefStateRepair.php `fetch_remote()`]（サブエージェント M1）
`ApiException` のステータス 0 を一律「未接続・認証切れ」（409）に分類していた。ステータス 0 は `ColorMeAdapter::client()` の未接続だけでなく、`HttpClient` の通信断（WP_Error）と `ColorMeClient` の JSON 破損でも使われる。リポジトリ自身の先例（`ColorMeAdapter::is_retryable_failure()`）は 0 を「通信断＝再試行対象」と扱っており、同じコードの解釈が食い違っていた。一時的な通信断でも UI が「Connections タブで再接続を」と案内し、副管理者では通らない再認可へ店舗を誘導しうる。**実ソースで確認済み**。
**修正:** 409 は 401/403 またはアダプタが `context['not_connected'] === true` で明示した場合だけ。`ColorMeAdapter::client()` が未接続を文脈で明示。ステータス 0 の通信断は 502。

### [R1-2][Medium][src/tabs/ToolsTab.tsx（完了通知）]（サブエージェント M2）
Scan/Repair の完了通知が `fixed` だけを見ており、`unverified`/`unavailable`（直っていない可能性が残る件数）があっても緑の「No records need repair.」/success になった。承認済み計画（「成功メッセージに混ぜず注意表示」）からの逸脱でもある。
**修正:** `unverified + unavailable > 0` のときは warning にし、件数と「下の表を参照」を本文に含める（Scan・Repair とも）。

### [R1-3][Medium][includes/Woo/Tools/PrefStateRepair.php `write_order()`/`write_customer()`]（実装者。R1-L9 の修正中に発見）
書込みの成否を確認していなかった。**`WC_Abstract_Order::save()` は保存中の例外を内部で握りつぶしてログに残すだけで ID を返す**（WC 11.1 の実ソース `abstract-wc-order.php:273-315` で確認）ため、他プラグインのフックが保存を妨げても呼び出し側からは成功に見え、ツールは「補正した」と報告してしまう。顧客側も `update_user_meta()` は同値更新でも失敗でも false で区別できない。サブエージェントの L9（Woo 書込み例外が REST を 500 にして件数を失う）に対する修正（`try_write()`）のテストを書いたところ、例外そのものが伝播しないことが分かった。
**修正:** 書き込んだ後に DB から読み直して確認し、一致しなければその1件だけを `skipped`（保存失敗）として先へ進む（`try_write()` + 読み直し検証）。テスト `test_a_record_that_cannot_be_saved_is_skipped_without_aborting_the_run`（`woocommerce_before_order_object_save` で例外を投げる）を追加。
