## 指摘
### [R1-1][High][includes/Admin/RestController.php:1022（get_run_verification）]
新設ルートの `run_id`（リソースを名指しするパスパラメータ）を `get_param()` で読んでいた。`get_param()` は GET でもクエリ文字列の同名値をパスより優先するため（`WP_REST_Request::get_parameter_order()`）、`?run_id=` で別 run のレポートが返る。CLAUDE.md「リソースを識別するパスパラメータは必ず `get_url_params()` で取得すること」に違反。
同一ファイルの既存 4 箇所（`get_run` / `cancel_run` / `get_run_report` / `retry_job` の `id`）にも同じパターンが残っていたため、CLAUDE.md の「同一ファイル内の類似呼び出しを横展開」ルールに従い併せて修正。
**修正方針:** `run_id_param()`（`get_url_params()` 経由）を追加して 5 箇所を統一、`retry_job` は `get_url_params()['id']`。回帰テスト `test_run_routes_read_the_run_id_from_the_path_not_the_query_string` 追加。

### [R1-2][High][includes/Admin/RestController.php（rebuild-mappings args）/ src/tabs/ToolsTab.tsx:runRebuild]
管理画面は初回リクエストで `{ platform, cursor: null }` を送るが、`cursor` の `args` スキーマが `type: string` のみだったため `rest_parse_request_arg` が JSON の null を型エラーとして 400 を返し、**Rebuild links が UI から一度も成功しない**（PHPUnit / `wp eval` の E2E は cursor を送っていなかったため検出できなかった）。
**修正方針:** スキーマを `type: ['string','null']` にし、UI 側も null のときは `cursor` を送らない。回帰テスト `test_rebuild_mappings_accepts_a_null_cursor`（`set_body_params(['cursor' => null])`）追加。

### [R1-3][High][includes/Woo/Tools/MappingRebuilder.php:scan_orders]
`wc_get_orders([... 'meta_query' => 所有メタ])` で受注を絞れる前提だったが、`meta_query` を解釈するのは HPOS の `OrdersTableQuery` だけで、レガシー（投稿型）ストレージでは WC 9.2+ が非対応引数として**無視**し `doing_it_wrong` を出す（`WC_Order_Data_Store_CPT::query()` の `$unsupported_args = ['meta_query','field_query']`。実ソースで確認）。レガシー構成では全受注が返り、`_cbjp_remote_order_number` を持つ他プラットフォーム由来の受注まで自プラットフォームの mapping として upsert され、次回 import が他プラットフォームの受注を更新しうる（独立レビュー指摘）。
**修正方針:** `OrderUtil::custom_orders_table_usage_is_enabled()` が真のときだけ `meta_query` を付け、どちらの構成でも取得後に `_cbjp_platform` を検証したものだけを upsert。cursor の前進判定を「クエリが返した件数（scanned）」に分離（除外行が多いページで走査し切ったと誤認しないため）。CLAUDE.md・03 §10.3 に反映。

### [R1-4][High][includes/Woo/Tools/SampleCleanup.php:can_delete_user]
`wp_delete_user()` は capability を一切見ない（`wp-admin/includes/user.php`）。ルートの権限は `manage_woocommerce` のみで、shop_manager は `delete_users` を持たないため、WP 管理画面ではできないアカウント削除をこのエンドポイント経由で実行できた（独立レビュー指摘）。
**修正方針:** `can_delete_user()` に `current_user_can( 'delete_user', $user_id )` を追加（満たさなければ unlink）。preview も同じ述語を使うため表示も整合。テスト `test_shop_manager_can_only_unlink_customer_accounts` 追加、既存テストは管理者として実行するよう `set_up` を変更。

### [R1-5][Medium][includes/Woo/Tools/SampleCleanup.php:owned_attachment_ids（旧）]
所有添付の削除だけが mappings を経由せず `_cbjp_platform` メタの全走査で行われていた。mappings を失った店舗（＝ Rebuild links が想定する状況）でクリーンアップを実行すると、商品・タームは1件も消えないまま取り込み画像だけが `force_delete` され、残った商品・カテゴリが画像を失う（独立レビュー指摘）。
**修正方針:** `deletable_attachment_ids()` に置き換え、`_cbjp_platform` + `_cbjp_source_url` を持つ添付のうち「親投稿が無い／削除済み（または mapping 経由で消える商品の画像）かつ既存タームの `thumbnail_id` でない（または消えるタームの画像）」孤児だけを対象にする。候補は毎回全件判定し予算分だけ削除（`has_more` は残候補数で判定）。テスト2件追加（残存商品の画像・残存タームの画像が保持される／mapping ありなら消える）。

### [R1-6][Medium][src/components/VerificationReport.tsx:isReconciled（旧）/ includes/Sync/VerificationReport.php]
`processed`（この run の取得件数）と `existing`（プラットフォーム全体のリンク済み実在数）はスコープが異なるのに直接比較し、`existing > processed`（過去の run で取り込み済み・ASP 側で減った等）でも「Some records fetched from the platform are not in WooCommerce」という事実と逆の Notice を出していた（独立レビュー指摘）。
**修正方針:** 行ステータスを方向付き（`missing` / `fewer` / `more` / `amount` / `reconciled`）にし、該当する Notice をそれぞれ出す。バックエンドの数値は変更なし。03 §10.4 の解釈を更新。
