## 指摘

### [R1-1][High][src/tabs/ExportTab.tsx `save()`]（自己レビューで検出・修正済み）
プラットフォーム選択後に`save()`を呼んだ直後、応答が届く前に別プラットフォームへ切り替えると、
古い応答の`setMappings(data)`が新プラットフォームの表示を上書きしてしまう
（`ImportTab.tsx`の`requestedPlatform`パターン未適用）。
**対応:** `platformRef.current !== requestedPlatform`ガードを`save()`にも追加。

### [R1-2][High][includes/Woo/Support/MappingCandidates.php `order_statuses()`]
`wc_get_order_statuses()`はコアの7ステータスに加え、WooCommerce Blocksが登録する
`wc-checkout-draft`（"Draft"）を含む。`OrderWriter::apply_status()`は`wc_get_order_statuses()`に
存在するキーを無条件に受け入れるため、ユーザーがASPステータスをこれへマップすると、
取り込んだ受注が**`woocommerce_cleanup_draft_orders`（日次cron）により24時間経過後に完全削除される**
（wp-envのWooCommerceソース `src/Blocks/Domain/Services/DraftOrders.php::delete_expired_draft_orders()`
で実装を確認: `wc_get_orders(['status'=>'wc-checkout-draft', 'date_modified'=>'<=...'])` →
`$order->delete(true)`）。
**対応:** `checkout-draft`を候補から除外する`EXCLUDED_ORDER_STATUSES`定数を追加し、除外理由を
docblockに明記。回帰テスト`test_order_statuses_excludes_checkout_draft`を追加。

### [R1-3][High][includes/Admin/RestController.php `asp_mapping_candidates()`]
アダプタ戻り値の防御的検証がトップレベルの`is_array()`のみで、各要素が`{id,name}`形状か検証して
いなかった。同ファイルの`connection_fields()`が`instanceof ConnectionField`で防御している
（アーキテクチャ原則8「アダプタ拡張点の信頼境界」）のと非対称。契約違反アダプタ（外部Pro拡張等）が
非配列要素や`id`/`name`欠損の要素を返すと、フロントの`Array.prototype.map`やReactの子要素描画が
例外を投げ、Exportタブ全体がクラッシュしうる。
**対応:** `normalized_candidate_list()`を新設し、各要素が`is_array()`かつ`id`/`name`とも
`is_scalar()`であることを検証、不正な要素だけを黙って除外する形に変更。回帰テスト
`test_get_settings_mappings_filters_out_malformed_adapter_candidates`を追加。

### [R1-4][Medium][src/tabs/ExportTab.tsx `MappingSection`]
保存済みの値が`targetCandidates`に存在しない場合（決済ゲートウェイの無効化、配送ゾーン
インスタンスの削除、ASP側メソッドの廃止等）、ネイティブ`<select>`はどのoptionにも一致せず
先頭（「未マッピング」）を表示するが、`edited`/DBには古い値が残ったままになり、表示と実データが
食い違ったうえ同じ選択肢を選び直しても解除できなくなる。
**対応:** 現在値が候補に無い場合、`(no longer available)`ラベル付きの一時optionを差し込み、
表示と選択解除の両方を可能にした。

### [R1-5][Medium][includes/Admin/RestController.php `save_settings_mappings()`]
`asp_mapping_candidates()`がGETだけでなくPUTでも呼ばれ、ColorMeでは保存のたびに
`categories.json`+`payments.json`+`deliveries.json`の3リクエストが追加で発生していた。
実行中のインポート/エクスポートジョブと同じ`RateLimiter`バケットを奪い合い、
`RateLimitExhaustedException`でジョブが一時停止しうる。
**対応:** PUTの応答から`asp_candidates`/`woo_candidates`を外し、GETのみが返す設計に変更
（保存操作そのものでは候補は変化しないため、フロントは直前のGETの候補をそのまま使い回す）。
`src/types.ts`に`SettingsMappingValues`（4マップのみ）を新設し`SettingsMappings`が継承する形に分離、
`ExportTab.tsx`の`save()`は保存後も既存の`mappings.asp_candidates`/`woo_candidates`を保持するよう修正。
回帰テスト`test_save_settings_mappings_response_omits_candidates`を追加。

### [R1-6][Medium][includes/Admin/RestController.php `asp_mapping_candidates()`]
`catch ( Throwable )`が認証エラー・レート制限枯渇・スキーマ崩壊を区別せず握り潰し、ログも残さず、
応答にも失敗の痕跡が無かった。UIは「No options available yet.」を出すが、店舗オーナー・サポートが
「未接続」と「レート制限に当たっただけ」を切り分けられない。
**対応:** 例外クラス名のみ（個人情報禁止ルール）を`Support\Logger`へ`warning`記録するよう追加。
回帰テスト`test_get_settings_mappings_logs_a_warning_when_adapter_candidates_fail`を追加。

### [R1-7][Medium][src/tabs/ExportTab.tsx セクション構成]
カード冒頭の文言が「Map WooCommerce data to the connected platform before exporting」だったが、
実際は4テーブル中3つ（payment/shipping/status）が`MethodMap`と共用の**インポート方向**マップ
（ASP側→Woo側）であり、文言・レイアウトの両方がユーザーを誤読させる。さらにE2-3の`push_order`が
必要とするWoo→ASPのマップは、ASP→Wooが単射とは限らない（複数のASP値が同じWoo値へ寄りうる）ため
機械的な反転では代用できない。
**対応:** 冒頭文言を修正し、payment/shipping/statusの各テーブルに「importingと共用」である旨の
`help`テキストを追加。E2-2/E2-3への申し送り事項として`docs/03-design-decisions.md` D19に
逆引きの曖昧性についての注記を追加。
