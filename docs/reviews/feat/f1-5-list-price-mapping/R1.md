## 指摘

### [R1-1][High][includes/Adapters/ColorMe/ColorMeAdapter.php:412]
`fetch_product_by_remote_id()` が `$this->product_transformer()` の呼び出しを
`try { … } catch ( Throwable $exception )` の**内側**に置いていた。
`product_transformer()` は初回呼び出し時に `GET /v1/shop.json` を叩いて税設定を取得するため、
この呼び出しが失敗（認証切れ・レート制限・5xx等）すると `ApiException` が投げられるが、
そのまま同じ catch に飲み込まれ「この商品1件だけの変換失敗」として `null` を返し、
`log_transform_failure()` で通常の行レベル失敗と同じログしか残らない。

**失敗シナリオ:** ジョブ実行中にアクセストークンが失効した状態で
`fetch_product_by_remote_id()`（サンプル選定のフォールバック等で呼ばれる）が呼ばれると、
実際にはAPI接続自体が壊れているにもかかわらず「この商品は解決できなかった」という
個別行の欠落として静かにスキップされる。ジョブ全体を失敗させリトライに委ねるべき
基盤障害が、静かな部分移行（CLAUDE.mdが繰り返し禁止しているパターン）として現れる。

**修正方針:** `product_transformer()` の呼び出しを try節の外に出し、
基盤取得の失敗は通常どおり呼び出し元へ伝播させる（`fetch_products()` と同じ扱いに揃える）。

**状態: 修正済み**（`product_transformer()` をtry節の外へ移動。回帰テスト
`test_fetch_product_by_remote_id_propagates_shop_json_failures_instead_of_swallowing_them`
を追加し、`shop.json` が401を返すケースで `ApiException` が呼び出し元まで伝播することを確認）。

## 対象外指摘（差分範囲外）

- [R1-X1][High][includes/Adapters/ColorMe/ColorMeAdapter.php:305,371,390]
  `order_transformer()` にも同種のパターンがある。`fetch_orders()`/`fetch_latest_orders()` は
  `$this->order_transformer()->transform($item)` を `transform_rows()`（内部で1行ずつ
  `try/catch(Throwable)` する `transform_rows_flat()`）に渡している。`order_transformer()` は
  初回呼び出し時に `payments.json`/`deliveries.json` を叩くため、この基盤取得が失敗すると
  「1件目の受注行の変換失敗」として飲み込まれ、後続行でも同じ理由で毎回失敗し続ける
  （`$this->order_transformer` がnullのまま再試行されるため）。結果としてページ全体が
  「0件変換」で完了扱いになりうる。本PRの差分には含まれない既存コードのため、
  ここでは修正せず記録のみ行う。別issueとして切り出すことを推奨。
