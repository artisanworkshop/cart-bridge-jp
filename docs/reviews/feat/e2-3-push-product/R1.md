## 指摘

### [R1-1][High][includes/Adapters/ColorMe/ColorMeAdapter.php ensure_option_values()]
`POST /products/{id}/options` の `option.values` は swagger実測で **オブジェクトの配列**
（`[{"name":"赤"}, ...]`、`items.type=object`・`required:["name"]`）だが、実装は
`axis_values()` が返す**文字列配列**をそのまま送っていた（`GET /products/{id}` の**レスポンス**側
`values`は文字列配列だが、**リクエスト**側スキーマは別物）。実機では422になり、variable商品の
バリエーションが1件も作られない＝本PRの中核機能が機能しない。テストのフィクスチャも誤った
リクエストスキーマを固定化していたため検出できなかった。
**修正方針:** `array_map(fn($v) => ['name' => $v], $axis_values)` を送る。テストのアサートも
`[['name'=>'Red'],['name'=>'Blue']]` に修正する。

### [R1-2][High][includes/Adapters/ColorMe/ColorMeAdapter.php サブリクエストの catch(Throwable)]
追いPUT・`ensure_option_values()`・`push_variant_details()`・`fetch_product_detail()`・
`push_images()` が全て `catch ( Throwable $exception )` で握り潰しており、
`RateLimitExhaustedException` も飲み込む。`Sync\Exporter::process_items()`（PR #40 G1-1）は
「レート制限はジョブ全体を一時停止すべきシグナル」として専用catchで再スローする設計だが、
本実装のサブリクエストがそれより先に握り潰すため、バケット枯渇後は全商品が
「本体だけ作成→サブリクエスト全滅」で進み、ジョブがpausedにならずcompletedで終わってしまう。
**修正方針:** 各サブリクエストのcatchで`RateLimitExhaustedException`を先に再スローする。

### [R1-3][High][includes/Adapters/ColorMe/Transform/ProductTransformer.php base_payload() / to_push_amount()]
税設定不明で価格を1つも解決できなかった場合でも、`display_state`は`$product->status`由来の
`showing`のまま商品がPOSTされ、無価格（0円相当）の商品が実店舗に公開されうる
（CLAUDE.mdアーキテクチャ原則9「楽観的デフォルト（公開...）は金銭的リスクに直結する」）。
**修正方針:** 価格を1件も解決できなかった場合、`display_state`を`hidden`へ強制する。

### [R1-4][Medium][includes/Adapters/ColorMe/ColorMeAdapter.php sync_variants() のバリエーション突合]
突合キーを`option1_value`/`option2_value`の**スロット位置**でそのまま比較しているが、
`ensure_option_values()`は軸を**名前**で解決する（スロット位置は保証しない）。ColorMe側の
既存オプションslot順（作成順で決まる）とWoo側の軸抽出順が食い違う更新ケースでは、
名前は正しく解決されてもスロット位置がずれ、全バリエーションが恒久的に
`PRODUCT_VARIANT_PUSH_INCOMPLETE`になりうる。
**修正方針:** 突合キーをスロット位置ではなく `{軸名: 値}` の名前キー付き連想配列から組み立てる
（リモート側は`option1`/`option2`ネストオブジェクトの`name`/`value`を使う）。

### [R1-5][Medium][includes/Adapters/ColorMe/ColorMeAdapter.php sync_variants()]
ColorMeはオプション追加で全組み合わせ（直積）を自動生成するため、Woo側に無い組み合わせの
バリエーションが残り、警告なく親の`sales_price`で販売可能なまま残る
（原則4により削除もできない）。
**修正方針:** リモートvariant数がcanonical variant数を超えたら専用警告を積む。

### [R1-6][Medium][includes/Adapters/ColorMe/ColorMeAdapter.php サブリクエストの警告分類]
`PRODUCT_*_INCOMPLETE`系を無条件に`indicates_unresolved_reference()`（retry対象）へ入れたため、
恒久的な失敗（画像5MB超の422・オプション上限2つ超過・軸名不一致等）でも
checksumが永久にキャッシュされず、毎回のexportで同じ無駄なリクエスト列が繰り返される。
**修正方針:** サブリクエストの失敗をステータスコードで分類し、429/5xx/通信断のみretry対象の
警告、それ以外の4xxは終端警告（retry対象外）にする。

### [R1-7][Medium][includes/Sync/Exporter.php 変種mapping書き戻し]
親商品側にはPR #40 G3で「remote_idが変わったら旧行を`delete_one()`」の修正が入っているが、
新設したvariant書き戻しには同じ処理が無い。Woo側の属性値リネーム等で同じlocal_idに対し
ColorMeが新しいvariantを自動生成した場合、旧remote_idの行が孤児として残りうる
（CLAUDE.mdに明記された既知パターンの横展開漏れ）。
**修正方針:** 書き戻し前に`find_remote_id()`で既存variant remote_idを引き、異なる場合は
`delete_one()`してからupsertする。

## 対象外指摘（差分範囲外の既存コード）
- `docs/review-backlog.md` の `e2-2-exporter-core/R2-M3-price-fallback`
  （`ProductReader::price_fields_for_simple/variable`が価格復元不能時に`'0'`を返し、
  `PRODUCT_PRICE_INVALID`がexport blocking/retry-worthyどちらでもない）は、本PRで
  「実際にColorMeへpushされる」経路が初めて有効になったことで実害が顕在化する
  （0円商品が恒久的にASP側へ作成・公開されうる）。ProductReader自体は本PRの差分範囲外
  のため修正対象にしないが、ユーザーへの確認事項として最終報告に残す。
- `ALL_VARIATIONS_EXCLUDED`（`ProductReader`）がretry-worthyでないため、全バリエーション
  除外のvariable商品が「最安値の単純商品」として公開・確定する（既存コード、本PR差分範囲外）。
- `OrderReader`/`CustomerReader`のextras欠落（backlog `e2-2-exporter-pr-b/G1codex-M-*`）は
  `push_order`/`push_customer`実装時に再燃する（次PRのスコープ）。
