## 指摘

### [R1-1][High][src/components/RunProgress.tsx:全体 / src/tabs/ImportTab.tsx:1039-1093]
`RunProgress` は dry-run・import 両方の結果セクションで共用しているが、CSVレポートのダウンロード
ボタン（エンティティ単位・全体）を無条件に表示している。バックエンド（`Sync\Importer::process_items()`）
は `cbjp_dry_run_items` への記録を `$is_dry_run` が true の場合のみ行い（`docs/03-design-decisions.md`
§10.4 でも「dry-runレポートCSVダウンロード」と明記）、実移行（`import`）ジョブの run_id では
このテーブルに1行も記録されない。実機確認済み: 実移行run（`8b4a1ca1-...`）に対する
`wp_cbjp_dry_run_items` の該当行数は0件（同条件のdry-run runは25件）。
結果として「Import results」側の「Download this entity's report (CSV)」「Download full report (CSV)」は
200を返すもののBOM+ヘッダー行のみの空レポートを生成し、ユーザーに「警告0件で完璧に移行できた」
という誤った印象を与えかねない。
**修正方針:** `RunProgress` にレポート機能の可否を示すprop（例: `reportsAvailable: boolean`）を追加し、
dry-runセクションのみ `true` を渡す。importセクションではCSV関連のUI（チェックボックス・ダウンロード
ボタン群）を非表示にする。

### [R1-2][Medium][src/hooks/useRunPolling.ts:398-406]
`poll()` の `.catch()` はエラーメッセージを state にセットするのみで、次の `setTimeout(poll, ...)` を
スケジュールし直していない。そのため一時的なネットワークエラー（Wi-Fi瞬断・タイムアウト等）が
1回でも発生すると、そのrunのポーリングは永久に停止する。復旧手段はページ全体のリロードしか無く、
特に実移行（数百件規模で数分かかりうる）の途中でこれが起きると、進捗・完了・警告の把握が
リロードするまで一切できなくなる。
**修正方針:** `.catch()` 内でも成功時と同様に非終端runとみなして `setTimeout(poll, POLL_INTERVAL_MS)`
を再スケジュールし、次の成功時に自動でエラー表示をクリアする（既存の `setError(null)` で対応済み）。

### [R1-3][Medium][src/tabs/ImportTab.tsx:991-1050]
「Preview results」「Import results」カードの「Clear」ボタンが、runがterminal状態かどうかに関わらず
常に有効になっている。実移行（`import`）が実行中（Action Scheduler側でバックグラウンド進行中）の
状態で「Clear」を押すと、localStorageの `run_id` とUI stateが破棄され、そのrunを追跡・キャンセルする
唯一の手段を失う（DBの実行自体は止まらず裏で継続する）。誤クリックのガードが無いため、
実データを書き込み中の実移行に対しては特にリスクが高い。
**修正方針:** `dryRunTerminal` / `importTerminal` が `true` になるまで「Clear」ボタンを `disabled` にする。

### [R1-4][Medium][src/tabs/ImportTab.tsx:733-748 / src/components/LimitsUpsellNotice.tsx]
dry-run完了時に `setDryRunTotals(totals)` で総数キャッシュを**丸ごと置き換えて**いるため、
（例）先に全エンティティでdry-runを実行した後、同一プラットフォームのまま商品だけを対象に
再度dry-runを実行すると、直前まで判明していた受注・顧客等の正確な総数が失われる
（`totals` はその回のdry-runに含まれるエンティティしか含まない）。
その後「Run import」を実行して上限に達した場合、`LimitsUpsellNotice` は本来出せたはずの
「◯件中◯件を無料版で移行済み。残り◯件はPro版で」という具体的な案内ではなく、
「上限に達しました。dry-runで確認してください」という一般的な文言にフォールバックしてしまう
（D15/§10.3が求める「具体数で表示」という要件を、直前の情報が使えるのに使わずに後退させる）。
**修正方針:** `setDryRunTotals` を置き換えではなくマージにする
（`setDryRunTotals((prev) => ({ ...prev, ...totals }))`）。

## 対象外指摘（差分範囲外）

- [R1-X1][Medium（対象外）][includes/Sync/JobManager.php:133-146 / RestController::cancel_run()]
  `cancel_run()` はDB上のjob状態を直接 `cancelled` に更新するのみで、Action Scheduler側で
  実行中の `process_job()` を中断しない。あるページ処理の実行中に外部からcancelされた場合、
  `process_job()` はページ処理完了後に再度 `find($job_id)` した古いstatusチェック（関数冒頭のみ）を
  通過済みのため、`complete_job_and_advance()` が無条件に `STATUS_COMPLETED` を書き込み、
  直前にcancelされた状態を上書きしてしまう競合状態がありうる。本PRでCancelボタンをUIに
  初めて露出させたことで顕在化しやすくなるが、修正対象は `includes/Sync/JobManager.php`
  （本PRの差分範囲外）のため対象外指摘とする。
