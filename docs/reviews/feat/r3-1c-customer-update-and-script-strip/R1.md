## 指摘
### [R1-1][Medium][includes/Woo/Support/HtmlText.php:SCRIPT_STYLE_ELEMENT（自己レビュー＋A-1）]
文字列全体を正規表現で探していたため、属性値（`<p title="<script>">`）・コメント（`<!-- <style> -->`）・CDATA の中の `<script>`・`<style>` という文字まで要素の開始と見なし、
閉じタグが無ければ末尾まで、後ろに本物の `</script>` があればそこまでの説明を消していた（wp-env で実測: `<p title="<script>">keep me</p><p>after</p>` → `&lt;p title=&quot;`。kses だけなら後ろは残る）。
Canonical が変わるので取込み済み商品は次の取込みで欠けた説明に上書きされる。入力はまれで ColorMe 側の元の値は残るため Medium（データ損失だが、まれな入力・元データあり）。docblock と docs の「ブラウザも残りを中身として読む」はこれらの文脈では誤り。
**修正方針:** 開始タグを kses と同じ区切り（`wp_kses_split()` の正規表現）で見つけ、中身はブラウザと同じ規則で最初の閉じタグまで読む。閉じタグが無ければ何も除かない。コメントの中は同じ規則で除く。
**対応:** 除去を区切りの走査に作り直した（`HtmlText::sanitize_post_html()` の内部。属性値・CDATA の中は対象外、閉じタグ無しは除かない、コメントの中も同じ規則で除く、JS の `a<b` をタグと見なさない。
テキストに `<` が無いので除いた前後から新しい開始タグはできず、繰り返しは不要になった）。テストに「何も除かない」入力 6 件（属性値・画像の alt・CDATA・閉じていないコメント・閉じタグ無し・属性値の後ろの本物の要素）を足した。
WP の HTML API（`WP_HTML_Tag_Processor`）も検討したが、コメントの中の `<script>`（kses が中身を文字として出す）と閉じタグ無しを別に扱う必要があり、kses と同じ区切りで十分と判断した。

### [R1-7][Medium][includes/Woo/Support/HtmlText.php（自己レビュー。R1-1 の修正中に実測）]
最初の作り直しは区切りと閉じタグを正規表現で探していたため、閉じタグの無い `<script>` が多い入力（640KB）で 1.3 秒、`>` の無い `</script ` が多い入力（720KB）で 5 秒かかり（探し直しが二乗）、
約 1MB のコメントでは遅延一致が PCRE の上限に達した（除去を諦める経路に落ちる）。独立レビューが測った性能は最初の正規表現のもので、作り直した後には当てはまらなかった。
**対応:** 区切りと閉じタグを `strpos()`・`stripos()` で探し、閉じタグの見つからなかった要素名は覚えて探し直さないようにした。PCRE が失敗する経路が無くなったので、失敗時の扱い（と、それを単独で確かめるために public にしていた
`strip_script_and_style()`・そのテスト）を除いた。実測（dev サイト）: 上の 2 つの入力は 0.1ms・31ms（除去の分）、1MB のコメントは 1ms。kses 自体が同じ入力に 100〜500ms かかり、除去の上乗せはその 1〜3 割。

### [R1-2][Medium][.claude/skills/rehearse-colorme/php/check-import.php（A-2）]
script/style の中身が残っていないかを、ColorMe の生の中身で Woo の保存値に `str_contains` していた。kses は文字の `&` `<` `>` を実体参照にするので、`if (a && b)`・`a < b`・`.a > .b` のような中身は残っていても検出できない（fail-open。skill-scripts.md の趣旨に反する）。`preg_match_all()` の失敗も黙って飛ばしていた。
**修正方針:** 実体参照を戻した保存値でも探す。PCRE の失敗は MISMATCH として報告する。
**対応:** 上記のとおり直した（`html_entity_decode( ENT_QUOTES | ENT_HTML5 )` した値でも探す、`false` なら MISMATCH）。
