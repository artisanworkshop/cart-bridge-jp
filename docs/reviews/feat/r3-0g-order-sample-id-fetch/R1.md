## 指摘

### [R1-1][Medium][includes/Sync/SampleSelector.php:69, 89-90（旧行番号）]
`SampleSet::$order_remote_ids` は `fetch_latest_orders()` の戻り値を件数で切らず、重複も除かずに
そのまま保存していた。product/customer は連想配列（重複排除）＋`array_slice`（`PRODUCT_HARD_CAP`/
`CUSTOMER_CAP`）で守っているのに対し、受注だけ上限が無かった。

main では `order_remote_ids` を読む箇所が1つも無かったため無害だったが、本PRで
`Importer::run_sample_page()`/`JobManager::process_page()` がこのフィールドを消費するようになった
（issue #38 の本題）ことで、`fetch_latest_orders( $limit )` の「最新 $limit 件」という契約
（アーキテクチャ原則8: アダプタ拡張点の信頼境界。ドキュメント上の契約でしかなく実行時に強制されない）
に違反する外部アダプタが $limit を超える件数・重複を返した場合、超過分だけ余分な
`fetch_order_by_remote_id()` 呼び出し（レート制限の浪費）が発生する経路になった。
ColorMeAdapter 自身は末尾で `array_slice($orders, 0, $limit)` しているため安全だが、
`cbjp/adapters/register` 経由の外部アダプタは信用しない、という既存方針（CLAUDE.md）に反する。

**根拠:** `SampleSelector::select_and_persist()` の該当行を読み、`git grep order_remote_ids main`
で main では読み手が存在しないことを確認。作成数自体は `LimitPolicy`（累積10件）で守られるため
データ破壊・二重作成には至らないが、`process_items()` は `remote_amount` をchecksum一致スキップに
関わらず全 processed 分で加算するため、重複IDがあれば検証レポートのASP側受注合計も二重に計上されうる。

**判定:** 修正
**修正方針:** `$order_remote_ids` を連想配列（`$order_remote_ids[$order->number] = true`）に変え、
product/customerと同じ `array_slice( array_map('strval', array_keys(...)), 0, SAMPLE_ORDER_LIMIT )` で
上限・重複排除する。`MockPlatformAdapter` に `latest_orders_override` を追加し、契約違反アダプタ
（$limit超過・重複あり）でもユニークな10件に収まることを `SampleSelectorTest` で検証。
`mutate-check.sh` で修正を戻すと当該テストが CAUGHT になることを確認済み。

## 対象外指摘（差分範囲外の既存コード）
なし。ただし運用上の注意点として1点: この修正の前に無料版で受注のサンプル移行を実行済みの店舗では、
（旧経路のカーソル走査で）サンプル外の受注も含めて `LimitPolicy` の累積枠（10件）を使い切っている
可能性がある。修正後に再実行すると、真のサンプル受注が `remaining<=0` で全てスキップされうる。
クリーンアップ→再選定（§10.2 #7）で回復できるためフェイルクローズ側に倒れており安全だが、
リリースノート等でユーザーに周知するかは別途判断が必要（最終報告で提示する）。

## 確認したが問題なし（独立サブエージェント・自己レビュー共通）
- 返却IDと要求IDの不一致（信頼境界）: `process_items()` はmappingキーに要求IDではなく
  `$item->remote_id()`（返ってきた受注自身の`number`）を使うため紐付けはずれない。
  `run_sample_stock_page()`のガードは「要求IDの商品に返ってきた商品の在庫を合成する」ために必要な
  ものであり、受注にはそのような合成が無いため不要（product/customerの`run_sample_page()`と同じ扱い）。
- ループ途中の`RateLimitExhaustedException`: `run_sample_page()`は全件取得を完了してから
  `process_items()`を呼ぶため、例外発生時は書き込みゼロ。`process_job()`のcatchでジョブがpausedになり
  `update_progress()`にも到達しないため、二重作成や進捗ずれは起きない（再取得の無駄はproduct/customerと
  同じ既存の限界で、本PRのスコープ外）。
- `JobManager::process_page()`の新しい`match`に`default`が無い件: `in_array(SAMPLE_ID_FETCH_ENTITIES)`の
  ガードの中にあり、値は3値と完全一致するため安全。`Importer::run_sample_page()`側には`default => throw`
  がある。
- 受注0件の店舗（`order_remote_ids=[]`）: 取得0回・`total=0`で安全に完了する。
- `limit_for('order')`がnull（Pro）の場合・dry-runは従来どおり全量カーソル走査。
- `LimitPolicy`の累積上限は`run_sample_page()`に渡しているため、クリーンアップ→再選定を繰り返しても
  上限回避はできない（原則7）。
- `VerificationReport`/`RunProgress.tsx`の`remote_amount`/`processed`の意味は変わらない
  （「この runで取得した分」のまま。件数が全件→10になるだけ）。
- `docs/03-design-decisions.md` §10.2 #4の追記は要検証#14・#18の区別を含め既存記述と矛盾しない。
- review-baseline/backlogとの重複指摘なし。
