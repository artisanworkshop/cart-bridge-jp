# Sync・Export・Tools・mappings の設計上の罠

> 取込み/書出しのパイプライン（`includes/Sync/**`）、Reader/Export、管理ツール（`includes/Woo/Tools/**`。サンプルクリーンアップ・リンク再構築・県コード修復）、`cbjp_mappings`/`cbjp_dry_run_items` を触るときに効く。
> CLAUDE.md の「コーディング規約」「アーキテクチャ原則」と併せて守る。ここは**触るファイルに対応するときだけ読み込まれる**パス指定ルール（`paths` frontmatter）で、内容は CLAUDE.md にあった項目をそのまま移したもの（issue/PR の番号は各項目に残してある）。

- `Sync\Importer::process_items()` は per-itemの警告を**dry-runのときしか永続化しない**（`$is_dry_run` ガード内の `DryRunItemRepository::insert_many()` が唯一の書込経路）。実移行の結果レポートに個別の警告は残らないため、「警告に情報を足せばユーザーが気付ける」という前提の設計は成立しない。またdry-run行は `existing_local_id` 列（`Admin\DryRunReportCsv::HEADER`）を持つので、`WarningCode::with_detail()` を足す前にその情報が既に行に載っていないか確認すること（PR #37 でdetailを追加→冗長と判明し取り消した）
- `Sync\JobManager::filter_and_order_entities()`は`can_fetch_customers=false`のアダプタ（BASE等）では顧客エンティティのジョブ自体を除外し、`Woo\Writer\OrderWriter::apply_customer()`も既存`mappings`の解決のみで新規顧客作成は行わない。受注インポート時に抽出した顧客（`CustomerExtractor`等、D12）を永続化する経路は現状存在しないため、そのようなアダプタを実装する際はImporter/JobManager側にプラットフォーム非依存の新しい拡張点を設計する必要がある（`docs/04-plan-base.md` B4-5参照。issue #26）
- `Sync\JobManager`は`RateLimitExhaustedException`を固定`PAUSED_RESUME_DELAY_SECONDS`（60秒）後に再試行する実装で、日次上限のような長時間（翌日まで等）の再試行遅延を指定する仕組みが無い。1日◯件のような上限を持つASP（BASE等）のexport実装時は、再試行遅延を可変にする拡張点をJobManagerに追加する必要がある（`docs/10-tasks.md` E5-1参照。issue #26）
- 破壊的操作（サンプルクリーンアップ等）のプレビュー件数は、実行側と**同じ判定関数**で算出すること。mapping 行数をそのまま出すと、他プラットフォーム所有・削除済み・親削除でカスケードする variation・共有画像の分が実行結果とズレる（PR #34 のボットゲートで G1-3/12・G2-2・G3-2 と 3 ラウンド連続で同種の指摘を受けた。`SampleCleanup::can_delete_entity()` を preview/run で共用する構成を参照）
- `_cbjp_platform` は email 突合による採用で別プラットフォームに書き換わる**可変**の所有メタ。「誰が作成したか」の判定にはこれを使わず、作成時にのみ書く不変マーカー `_cbjp_created_by_import`（値は作成プラットフォームID）を使うこと。可変メタで判定すると採用→リンク解除の後に作成元が削除できなくなる（G1-4/G2-1/G3-1）。**逆に「インポートが書いたデータを補正・更新するツール」の所有判定には `_cbjp_platform`（最後に書いたプラットフォーム）を使う**: `CustomerWriter` は採用した既存アカウントにも住所を書くため、不変マーカーで絞ると採用アカウントの誤りが直らない（`PrefStateRepair`。Codex/Copilot が不変マーカーへの絞り込みを繰り返し誤提案した。issue #46）。
  **D25（往復の向き。R3-1a）も `_cbjp_platform` を「このプラットフォームとの紐づけを取込みが作った」印に使う**（顧客は作成の印の一致も含む。判定は `Woo\Support\EntityOrigin` に集約）: 取込みで結ばれた実体はエクスポートしない（`ReadItem::$linked_by_import`）、エクスポートで結ばれた実体（印が無い）は取込みで上書きしない（`WooRepository`/`DryRunRepository`・在庫は `StockWriter`）。エクスポートは Woo に何も書かないので、この 1 ビットで mapping のある実体の向きが決まる。**取込みの writer に「既存の実体を結ぶが `_cbjp_platform` を書かない」経路を足すと、その実体はエクスポートで結ばれた扱いになって以後の取込みが止まる**（保護ロールの顧客がこの形なので、ガードは保護ロールを判定せず `CustomerWriter` に任せている）。逆に、エクスポートや他の経路で `_cbjp_platform` を書くと取込み品と判定されて送られなくなる（WC の商品複製はメタを写すので `woocommerce_duplicate_product_exclude_meta` で外している）
- `cbjp_mappings` を減らす・リセットする経路（クリーンアップ等）は、対応する実体を削除できない状況（権限不足等）では実行自体を拒否すること。unlink だけして mappings とサンプルセットを消すと `LimitPolicy` の累積カウントが消え、無料版上限（アーキテクチャ原則 7）を回避してデータを増やし続けられる（G1-11）
- エクスポート方向の `cbjp_dry_run_items`/`cbjp_mappings` は列の意味を読み替えて使う（スキーマ変更なし）。`cbjp_mappings` は `local_id`/`remote_id` とも方向を持たない設計だが、export方向は起点が常にWooローカルID（`MappingRepository::find_remote_id()`/`find_many_by_local_ids()` で逆引きする）。`cbjp_dry_run_items.remote_id`（`NOT NULL`・`UNIQUE(job_id, entity, remote_id)`）は新規作成候補（既存remote_idが無い）の行では一意性確保のためプレースホルダ `local:{local_id}` を入れ、`existing_local_id` 列にWooローカルIDを格納する（`Sync\Exporter::dry_run_row()` 参照）
- `cbjp_mappings.checksum` は `CHAR(64)`固定長（生のsha256 hex digest専用）で、export/import等どちらか一方の書込みに文字列プレフィックスを付けて名前空間を分けるような拡張はできない（MySQLが黙って切り詰める）。同じ`(platform, entity_type, remote_id)`行を複数の書込元が共有し、かつ「生ハッシュとして同じ値でも意味が異なる」場合は、`hash('sha256', 名前空間文字列 . $item->canonical_json())`のようにハッシュ対象（入力）側に名前空間を混ぜ込むこと（出力は引き続き64文字に収まる。`Sync\Exporter::export_checksum()`参照。issue発覚: E2-2 R1でimport/exportが同じchecksum列を生ハッシュのまま共有し、一方が他方の変更検知を破壊しかけた）
- `MappingRepository::upsert()`は`(platform, entity_type, remote_id)`のユニークキーで`ON DUPLICATE KEY UPDATE`するため、同じlocal_idに対してアダプタが異なるremote_idを返した場合（例: リモート側で削除された実体をupdate時に再作成した）、新remote_idで別行がINSERTされるだけで旧remote_idの行が孤児として残る。`find_remote_id()`/`find_many_by_local_ids()`はid昇順の最初の行を採用するため、以後は削除済みremote_idへ永久に再送し続け、無料版の累計カウントも余分に消費する。remote_idが変わったことを検知したら`upsert()`の前に`delete_one()`で旧行を消すこと（`Sync\Exporter::process_items()`参照。PR #40 G3）
- `Woo\WarningCode::indicates_export_blocking()`へ新しい警告コードを追加する前に、その警告が「フレッシュな環境でも既定で発火するか」を確認すること。`PRICES_INCLUDE_TAX_DISABLED`（`woocommerce_prices_include_tax=no`）は多くの実店舗の既定設定で、blocking化すると無料版の挙動確認自体ができなくなる店舗が続出する（`JobManagerExportTest`が実際に2件壊れて発覚。issue #43）。少数の境界条件でしか発火しない警告（`PRODUCT_PRICE_INVALID`等）とは扱いを分けること（後日談: エクスポート方向は issue #59 で `ProductReader` が税込へ換算するようになり、この警告自体を出さなくなった〔税計算OFFの既定環境では無変換が正しく、換算不能の税率状態だけを `PRICE_TAX_BASIS_UNRESOLVED` で blocking にした〕。`PRICES_INCLUDE_TAX_DISABLED` はインポート方向の `ProductWriter` だけが警告のみで出す）
- Writer側の変換（例: `AddressMapper`）を直しても、Canonicalが**変換前の生の値**を保持している限りchecksumは変わらず、`Importer`のchecksum一致スキップにより**取込み済みデータは再インポートで直らない**。Woo側に生の値が残らないと修正前後のデータは値だけで判別できず（入れ替え・巡回は一律の再適用が二重適用になる）、是正は「ASPから権威の値を再取得し、現在値が旧バグの出力と一致する場合に限り書き換える」ツールで行う（`Woo\Tools\PrefStateRepair`、issue #46）
- 新しい警告コードを定義しても、それを消費すべき既存の判定関数（`Woo\WarningCode::indicates_export_blocking()`等）への登録が漏れることがある。`ORDER_LINE_TAX_CLASS_UNSUPPORTED`（非課税・zero-rate等）は定義済みだったが`indicates_export_blocking()`に未登録のまま残っており、対応するASPの税区分と異なる税額で受注が恒久的に作成されうる状態だった（Codex・Copilotが独立に同一箇所を指摘。issue #45）。新規コードを定義した際は、それが本来どの既存判定関数の対象であるべきかを確認し、類似コードと横並びで登録すること
- **警告コードを足したら `Woo\WarningCatalog` に店舗向けの説明（重大度・原因・対処）を足す**（R3-0k。dry-run の CSV の `severity`・`message`・`action` 列）。全定数について両方向の説明があることと、
  `indicates_export_blocking()` のコードがエクスポートで `blocking` であることは `WarningCatalogTest` が強制する。同じコードを取込み（Writer）とエクスポート（Reader・アダプタ）の両方が出すなら向きごとに書く
  （通貨の不一致は取込みでは保存し、エクスポートでは送らない）。文言は docblock を写さず発生元のコードを読んで書く（R3-0k の調査で、止めるのに「警告のみ」と書いた docblock が 3 つあった）。
  detail を差し込む文言（`make()` の第 4 引数）は `sprintf()` に通すので `%` を `%%` と書く（`10%)` のままだと `ValueError` で detail の無い文言に倒れる）
- `Importer`/`Exporter`/`JobManager`/`SampleSelector` は mapping・無料版上限・サンプルのキーを**登録キーではなく `$adapter->id()`** から決める（`Importer` は `$adapter->id()` を `$platform` に使う）。`AdapterRegistry` は `id()` と登録キー（`cbjp/adapters/register` の配列キー）の一致を検証しないため、別キーで登録するモック・外部アダプタが `id()` を合わせないと、書込み用 Writer は登録キー・mapping は `id()` の名前空間、と黙ってズレる（`MockPlatformAdapter` の `platform_id` 引数で合わせる。PR #50 Codex 指摘）
- `JobManager::start_run()` は同時実行の判定（当初は `has_active_job_for_platform()`、issue #57 以降は下記の `is_platform_busy()`）で同一プラットフォームの同時実行を防ぐが、`JobManager::retry()` は当初このガードを経由せず、対象ジョブが `failed` であることしか見ずにrequeueしていた（E2-4 PR #53 G2/G3、Codex/Copilot指摘。issue #54）。`has_active_job_for_platform()` をそのまま `retry()` に足すだけでは不十分な点に注意: `start_run()` は対象runの全エンティティジョブを最初に `pending` で作成するため、失敗した1ジョブの**同じrunの兄弟ジョブ**まで「進行中」として誤検知し、正当な同一run内のRetryまでブロックしてしまう。対応として `JobRepository::has_active_job_for_platform_excluding_run( $platform, $run_id )` を新設し、対象ジョブ自身の `run_id` を判定から除外した（`JobManager::retry()` が異なる run のアクティブジョブを検知した場合は `start_run()` と同じ `RunAlreadyInProgressException` を投げ、`RestController::retry_job()` は既存の `run_in_progress_error()`（409）で応答する）。**判定（SELECT）と状態変更（別の SQL）は非原子的な check-then-act なので、判定だけではミリ秒単位で同時に届いた要求同士（`retry()` 同士、`retry()` と `start_run()`、`start_run()` とツール等）を防げない**（PR #56 G1）。issue #57（R3-0i (3)(4)）で次の形にした。**同時実行のガードを持つ操作を足すときは、この 3 点を全部守ること**: (1) 判定は `JobRepository::is_platform_busy()`（進行中のジョブ＋処理中の AS アクション。キャンセルしたジョブも処理中のページは書き終えるまで書き続けるため、`cancelled` の状態だけを見ると書込みと重なる）、(2) 判定から状態変更までを `Support\PlatformLock::run()` で囲む（REST は `RestController::run_exclusively()`。取得できなければ 409 `cbjp_run_in_progress`）、(3) ジョブの状態は `JobRepository::transition()`（期待する状態のときだけ）で変え、結果が false なら後続（エンキュー・次のジョブの開始）をしない。無条件の `update_status()` はテストの状態作成用。読むだけの表示（クリーンアップのプレビュー）はロックを取らない。ロックは再入できない（ロックの中から同じプラットフォームのロックを取る処理を呼ぶと 409 になる）
- 新しい例外型が「作成済みだが後続処理が中断した」のような回復可能な状態（remote_id 等）を運ぶ場合、それを消費する側（`Sync\Exporter`/`Importer`）は、**その状態を先に永続化してから**原因（`RateLimitExhaustedException`等）を再スローすること。永続化より前に再スローすると、運んできた状態が失われ、再開時に同じ実体を再作成する等の問題が起きる。`Adapters\PartialPushException` の処理（`Sync\Exporter::process_items()`）は、内側の `try/catch` で例外を通常の `PushResult` へ読み替えて mapping 書込み等の既存経路に流し、原因が `RateLimitExhaustedException` ならその変数を控えて**ループ本体の最後（mapping 書込みの後）**で再スローする（D21-A、issue #72）。R3-0b（push intent、issue #73）も同じ順序を踏襲すること
- 信頼境界（外部アダプタ・`PushResult`等）の値について「送信していない/確定した」ことを肯定形で判定する分岐は、正規化・フェイルクローズ済みのローカル変数ではなく、**正規化前の生の値**を見ること。`Sync\Exporter::process_items()` は未知の `$result->operation` を安全側の `skipped` へ正規化するが、この正規化後の値だけで「明示的に送信しなかった」と判定すると、`created`/`updated` を主張しつつ `remote_id` が空（2xxだがid欠損という契約違反そのもの）のケースも「送信しなかった」に混ざってしまう（issue #73 R1-1）。生の値と正規化後の値を同じスコープ内で使い分ける必要がある場合は、変数名・コメントでどちらを参照しているかを明示すること
- ページ内で複数アイテムが共有する上限カウンター（`Sync\Exporter::process_items()` の `$remaining` 等）を、ある1アイテムの副作用（mapping/intent の整合性修復など）に応じて事後的に補正する場合、単純な `++`/`--` の差分パッチにしないこと。元の計算（`LimitPolicy::remaining()`）が `max(0, ...)` 等でクランプされていると、同じページ内で複数回パッチを重ねたときにクランプで隠れていた超過分まで復活し、真の残数からズレて上限を超えて作成されうる（issue #73 G2-2 で単純増分を導入 → G3-1 で複数件同時発生時の破綻が発覚。都度 `LimitPolicy` から再計算する形に修正）。共有カウンターの事後補正は原則「ソースから再計算」を使うこと
- `tests/unit/Fixtures/FixedWooReader` は既定でページサイズ2件（`page_size` 引数省略時）。同一ページ内での複数アイテムの相互作用（例: 無料枠の奪い合い・自己修復の連鎖）を検証するテストで3件以上を1ページにまとめて処理させたい場合、明示的に `new FixedWooReader($items, count($items))` のように `page_size` を渡さないと、超過分が黙って「次ページ」に回り `run_page()` 1回では処理されないまま、検証したい相互作用自体が発生しない（issue #73 G3-1 のテスト作成時に一度気づかず、`error_log` でのトレースが必要になった）
- ロックの中で ASP を呼ぶ区間の期限（`Support\PlatformLock::TTL_LONG`）は最悪の所要時間から決める。HTTP 1 本は最悪約 540 秒（`HttpClient` の再試行・`Retry-After`・`RateLimiter::wait()`）、照会 1 件は ColorMe の受注で HTTP が最大 3 本（変換器の初回に `payments.json`・`deliveries.json`）。件数の上限だけでは足りず、時間予算（`PrefStateRepair::TIME_BUDGET_SECONDS`）と期限の両方が要る（PR #96 で Copilot が G1・G2 の 2 段階に指摘）。上限を変えると `PlatformLockTest::test_the_long_ttl_outlasts_the_slowest_locked_section` が落ちる。ロックの中に ASP を呼ぶ区間を足すときは見積もりを更新する
- 「止めるかどうかがプラットフォームの能力次第」の警告（`VARIATION_STOCK_MANAGEMENT_MIXED`）は `WarningCode::indicates_export_blocking()`（プラットフォーム非依存）に登録しないこと。登録するとバリエーション単位で在庫管理できるアダプタまで止まる。専用の判定（`indicates_variation_stock_mixed()`）を `Exporter` が `Capabilities`（末尾・既定 `false` の `supports_per_variant_stock_management`）と組み合わせて使い、警告が付いたときだけ `capabilities()` を呼ぶ。同じ事実を商品行と在庫行のように複数の Reader で判定するときは、判定関数と母集団（公開バリエーションすべて。価格不正で除外されるものも数える）を 1 箇所に共有して食い違いを防ぎ、両 Reader の一致をテストで固定する（D22、issue #52）
- **インポート方向でも、エクスポート方向の `checksum_salt()`（D24。次の項目）と同じ問題が起きる: 設定（`payment_map` 等）から解決する値は canonical の checksum に入らない**。設定が無いせいで欠けた結果を書いたアイテムの checksum を保存すると、後から設定しても checksum 一致で飛ばされて永久に直らず、再 dry-run も検証を飛ばして警告だけが消える（R3-0m: 決済/配送の未マッピング。`PAYMENT_METHOD_UNMAPPED`/`SHIPPING_METHOD_UNMAPPED` を `indicates_unresolved_reference()` に加えて checksum を保存しないようにした）。設定で結果が変わる警告を足すときは、その警告で checksum を止めるかを必ず決める
- **設定で「何を送るか」が変わる機能（画像アップロード等）は、オンの間だけ `export_checksum()` の入力へ印を混ぜる**（`Sync\Exporter::checksum_salt()`。D24）。混ぜないと、オフのまま export 済みの商品は checksum が一致して `push_product()` が呼ばれず、後でオンにしても永久に送られない。印はオンのときだけ・product だけ・アダプタが能力を持つときだけにして、**オフの checksum は従来と同一**に保つ（既存 mapping を全件再送にしない）。オフに戻すと印が外れて別の checksum になり、画像付きで送った商品は一度だけ再送される（許容）。設定の変更は run 中に許さない（`RestController::save_export_options()` が 409）ので、ページ内で 1 回だけ解決して使い回してよい。検証は JobManager 経由なら**専用の商品**で mapping の `checksum`/`synced_at` を見る（開発サイトの既存商品は未解決参照で checksum が保存されず、totals では再送か skip か分からない。`verify-with-mock-adapter` の落とし穴参照）
- `PlatformAdapter` のメソッドを `JobManager`/`Importer` の「高速経路」（無料版サンプルのID指定取得等）へ無条件で配線する前に、そのメソッドのdocblockが `UnsupportedOperationException` を許容しているかを確認すること。許容されている場合、対象エンティティが別の経路（`can_fetch_customers` によるcustomerのentity除外等）で完全にガードされていない限り、呼び出し側は例外を捕捉して元の経路（カーソル走査等）へフォールバックする必要がある。`fetch_order_by_remote_id()` は `fetch_orders()` 自体が全アダプタ必須で代替経路が無いにもかかわらず単一ID取得だけ `UnsupportedOperationException` を許容するという非対称な契約を持っており、`Importer::run_sample_page()`/`JobManager::SAMPLE_ID_FETCH_ENTITIES` に `order` を追加した際にこのフォールバックを最初は実装し忘れていた（issue #38、PR #86。Codex/Copilotが独立に同一箇所を指摘）
- `SampleSelector` のような、外部アダプタの戻り値を検証・正規化（重複排除・上限・型チェック等）した上で永続化するロジックに新しい検証を追加する場合、その値への**全ての**入口（新規選定 `select_and_persist()`・永続化済みデータの読込み `load()`・下流の消費側）に同じ検証を適用すること。新規選定側だけに追加すると、その変更が入る前に保存された、または契約違反アダプタが過去に保存した永続データが `load()` 経由でそのまま消費されてしまう（`SampleSet::from_array()` が保存された `null` を `strval(null) === ''` で空文字列に変換する経路も含む）。1回の指摘対応では入口を洗い出しきれず、`order_remote_ids` の正規化だけで3ラウンド（新規選定時の重複排除・上限 → 読込み時の同処理 → 空文字列の除去と要素の型検証）を要した（issue #38、PR #86 G1〜G3、Copilot指摘）
- `totals.unchanged` は `skipped` の内訳で、checksum 一致（変更なし）で書かなかった件数と、D25 の往復の向きで送らない／上書きしなかった件数のうち mapping があるもの（既に結ばれていて `used` に数えられている）だけを数える。dry-run の `created + updated + unchanged` が「移行できる件数」として Pro 案内（`LimitsUpsellNotice`）の内訳に使われるため、blocking・無料版上限・例外・契約違反のスキップで数えると「どの版でも移行できない」件数が消え、逆に「変更なしで書かない」新しい経路を足して数え忘れると「移行できない」が過大になる（issue #55、R3-0h）
