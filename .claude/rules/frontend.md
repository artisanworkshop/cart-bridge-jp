# フロントエンド（React/TypeScript）・管理画面の規約

> 管理画面 UI（`src/**`）と、そのアセット読み込み（`includes/Admin/Assets.php`）・OAuth ポップアップ・タブ/CSS を触るときに効く。
> CLAUDE.md の「コーディング規約」「アーキテクチャ原則」と併せて守る。ここは**触るファイルに対応するときだけ読み込まれる**パス指定ルール（`paths` frontmatter）で、内容は CLAUDE.md にあった項目をそのまま移したもの（issue/PR の番号は各項目に残してある）。

- OAuth認可ポップアップは `window.open()` をクリックハンドラから同期的に呼ぶ（await後だとブロックされうる）。`noopener`指定時は成否に関わらず戻り値が常に`null`になる仕様なので、ポーリング等でウィンドウハンドルが必要な場合は`noopener`を使わず、生成できたハンドル側で`.opener = null`を手動設定してreverse tabnabbing対策すること
- `wp-scripts build` はJSエントリー（例: `index`）からimportしたCSSを `build/index.css` ではなく `build/style-index.css`（`style-<エントリー名>.css`）として出力する。`wp_enqueue_style()` 側のパスをこれに合わせないと `file_exists()` ガードが常にfalseになりCSSが一切enqueueされない（`wp-components` のコアCSSも道連れで読み込まれず、管理画面が丸ごと無スタイルになった実例あり。`includes/Admin/Assets.php` 参照）
- 管理画面のタブナビゲーションは自前CSSではなくWordPressコア標準の `nav-tab-wrapper` / `nav-tab` / `nav-tab-active` クラス（`wp-admin/css/common.css` に定義済み）を使うこと。間隔・アクティブ状態の表示が無料で手に入る。自前CSSはコアクラスがカバーしない余白調整のみに留める（`src/App.tsx`, `src/style.css` 参照）
- ポーリングhook（`useRunPolling`等）の`refetch()`が一時的な通信エラーを内部でcatchして自動再試行する設計の場合、そのPromiseは通信の成否に関わらず正常解決する。呼び出し元が「`await refetch()`が解決した＝新しいstateが反映された」と決め打ちすると、一時的な失敗時に古いstateのまま後続処理（例: ボタンの再有効化）が進んでしまう。真に「新しいデータが届いた」ことを検知したい場合は、Promiseの解決ではなくstate自体（成功時のみ新しい参照になるオブジェクト等）の変化をeffectで監視すること（`src/hooks/useRunPolling.ts`, `src/tabs/ImportTab.tsx`のretryJob参照。issue #30）
- 複数ジョブから成るrunの「終端判定」（`isTerminal`: 全ジョブがcompleted/failed/cancelledのいずれか）と「成功判定」（全ジョブがcompleted）を混同しないこと。キャンセル・一部失敗したrunも`isTerminal`はtrueになるため、「完了時のみ出す」UI（全体レポートDL・アップセル集計等）を`isTerminal`だけでゲートすると、部分的・失敗した結果を完全な結果として提示してしまう。個別の判定（全ジョブcompleted）を別途用意すること（`src/components/RunProgress.tsx`のallCompleted参照。issue #30）
- WordPressコアが登録する`wp-components`等の共有アセットハンドルは、WooCommerce等の他プラグインが独自バージョンを登録しているとそちらが優先されることがあり、同じ`@wordpress/components`の`Notice`等でも環境によってレイアウト（例: `flex`+`padding: 8px 12px` vs `grid`+`padding: 12px`）が変わりうる。見た目の余白等を安定させたい箇所はアップストリームのデフォルトに依存せず自前CSSで明示的に上書きすること（`src/style.css`の`.components-notice.is-info`参照）
- 破壊的・本番書込み系の確認ダイアログ（`ImportTab.tsx`の本移行実行確認、`ToolsTab.tsx`のクリーンアップ確認）にネイティブ`window.confirm()`を使っている。ブラウザ拡張系の自動操作（Claude in Chrome等）やE2Eツールからクリックすると、ネイティブダイアログがレンダラーをブロックしてタブがフリーズし、ブラウザ再起動が必要になることがある（F1-8の実店舗テストで発生）。`ExportTab.tsx`の本番export実行確認はこの問題を避けるため`window.confirm()`を使わず、常時表示の`Notice`+`CheckboxControl`で実行ボタンをゲートする方式に置き換えた（E2-4。実行が成功したらチェックボックスを明示的に外し、`window.confirm()`と同様「実行のたびに再確認させる」強さを保っている）。新規に確認UIが必要になった場合はこちらの方式を踏襲すること。`ImportTab.tsx`/`ToolsTab.tsx`は未置換のまま残っている（`docs/review-backlog.md`の`e2-4-export-ui-e2e/confirm-ux-asymmetry`）
- 非同期処理（fetch effect・保存処理等）の古い応答が新しい状態を上書きしないようにするガードは、比較対象を「値の一致」（例: プラットフォーム名）ではなく**単調増加する世代カウンタ**にすること。値の一致だけで判定すると、同じ値へ短時間で戻った場合（例: プラットフォームA→B→A）に古いリクエストの応答を「最新」と誤認する。さらに、同じ状態を更新しうる複数の非同期処理（例: 取得のGETと保存のPUT）がある場合は、それら**すべてが同じ世代カウンタを共有**する必要がある。片方だけ導入してももう片方が古い判定方法のままだと同種のレースが残る（`src/components/MappingSettings.tsx`の`generationRef`参照。issue #39。R3-0m で `ExportTab.tsx` から移した）。`ToolsTab.tsx`は置換済み（issue #46）。**`ImportTab.tsx`には値比較の`platformRef`が残っている**（backlog `fix-46-pref-state-repair/R1-X1`）。**プラットフォーム単位の世代カウンタだけでは「同一プラットフォーム内で新しいrunが始まる」レースは検知できない**（世代はプラットフォーム切替時にしか進まない設計のため）。runの識別に紐づく非同期応答（例: run完了後に取得する付随情報）は、`useRunPolling`の`runIdRef`と同じ考え方でrun_idそのものも別途チェックすること（`src/tabs/ExportTab.tsx`の`exportRunIdRef`参照。E2-4 PR #53 G3、Codex指摘）。**応答に付けるタグも同じ**: 409 の一覧をプラットフォーム名と組にして照合すると A→B→A で古い応答が通る（R1 でそう作り、Copilot に再指摘された）。要求を出したときに単調増加の番号を控えて照合する（`useActiveRuns` の `selectionRef`・`activeRunsSeed()`）。利用側が「一覧ごとに 1 回」の判定に使う版も、プラットフォームの切替で 0 に戻さない（戻すと別プラットフォームの同じ番号で判定が飛ぶ。PR #95 G1-1〜G1-3）
- 複数の経路（マウント・run 完了・解除/保存の成功後）が同じ一覧 state を更新するときは、**全ての書き手を「取得関数の呼び出し」1経路に統一し、世代カウンタは取得関数の内側でだけ進める**。変更操作の成功時に世代を手動で進めてローカル配列を `filter` するだけの実装は、その世代で無効化された進行中の取得応答（新しく増えた行を含みうる）を捨ててしまい、行が黙って欠落する（PR #80: G1 で足した手動 bump が G2-1 の回帰を生んだ）。変更後は取得関数を呼び直すこと。あわせて、再取得失敗時に一覧をエラーで置き換えるのは「表示できる行が無い（`null` **または空配列**）」ときだけにする。`null` だけを見ると、前回0件で成功した後の失敗が空配列の早期 return に隠れ、新しい行もエラーも見えなくなる（G2-2。`src/components/PushIntentsPanel.tsx` 参照）
- サーバー側の真偽値設定（例: 画像アップロードのオン/オフ）を表示するチェックボックスは、**取得前は `null`**（未確定）と**取得後の `false`**を区別すること。`checked={value ?? false}` は両者を同じ見た目にするが、本番書込みを伴うボタンの活性化条件にこの式をそのまま流用すると、保存済みの値が実は `true` でも「取得中でオフに見える」間にボタンが押せてしまい、意図せず書込みが実行される。書込み系ボタンの `disabled` には、対象設定が `null`（未取得）であること自体を別条件として加える（`ExportTab.tsx` の `exportOptionsPending` 参照。issue #75 G1-3、Codex指摘）
- `@wordpress/components` は実行時に WP コア同梱の `wp-components`（依存抽出で外部化）が使われ、npm 版と実装が違うことがある。`ExternalLink` は npm 28.x が `rel="external noreferrer noopener"` を自動で付けるが、WP 7.1 コア版は `target="_blank"` だけで `rel` を付けない（実測。R3-0h）。`rel` などのセキュリティ属性は明示し、確認は npm のソースではなく実機の DOM で行う（`LimitsUpsellNotice.tsx`）
- 表示用の計算は純粋関数に切り出して Jest で単体テストする（`npm run test:js`＝wp-scripts 同梱。テストは `src/**/test/*.test.ts`）。`describe`/`expect` は `@jest/globals` から import する（`tsc --noEmit` が `src` 全体を型検査し、eslint の `import/no-extraneous-dependencies` が未宣言の依存を拒むため。グローバル型の `@types/jest` は入れていない。`src/components/test/upsell-breakdown.test.ts` 参照）
- run ごとの結果を前回値へマージして保持する state（dry-run の件数キャッシュ等）は、新しい run の開始時にその対象エンティティの前回値を捨てる。完了したジョブだけをマージする実装だと、新しい run の一部が失敗・キャンセルしたとき、そのエンティティに前回の値が残って今回の結果として表示される（上の isTerminal と allCompleted の区別とは別の問題。`withoutDryRunTotals()` 参照。PR #87 G1-1/G1-2）
- 世代カウンタを**進める** effect を削除・移動するときは、残る effect のどれかが進め役を引き継ぎ、世代を**読む** effect がそれより後ろに宣言されていることを確かめる。進め役が無くなってもエラーは出ず、全ての応答が「最新」と判定されて A→B→A の古い応答を捨てられなくなる（R3-0m: `ExportTab.tsx` の `platformGenerationRef` はマッピング取得 effect だけが進めていたため、Mappings タブへ移す際に画像設定の取得 effect へ移した）
- 別のタブへ選択中の platform を引き継ぐリンクは `tabHref( tab, platform )` で `#/<tab>?platform=<id>` を作り、受け取る側は `parseHash()` の値を**接続済みの platform に一致するときだけ**初期選択に使う（ハッシュは任意の文字列を含みうる。`src/hash-route.ts`。各タブは既定で先頭の platform を選ぶため、引き継がないと別 platform の設定を開いてしまう。PR #89 G1-1）
- 「移行できない」などの理由の案内先は、dry-run の CSV だけでなく Logs タブも挙げる（remote_id 欠損は CSV に行が作られず、Logs にだけ残る。PR #87 G1-3）
- 一覧を照会し続ける hook は、一覧が空になっても照会を止めない。止めると、タブを開いた後に別のブラウザで始まった run を見つけられず、それに頼る UI だけのガード（サーバーが拒否しない Mappings の保存）がすり抜ける。UI だけのガードは、最初の一覧を取得できるまでも止めておく（フェイルクローズ。`useActiveRuns` は空なら 30 秒ごと。PR #95 G1-4/G1-5）
- プレビューの件数で確認を取る破壊的操作は、そのプレビューと run が重なったら（プレビュー時点・今・プレビュー後に run を見た）、取り直すまで実行させない。件数 0 のプレビューでは確認ダイアログ自体が出ないため、run の途中に取ったプレビューのまま実行すると、run が書いたデータを確認なしで消す（`isCleanupBlocked()`。「今の一覧だけで判定」にした最初の実装が退行だった。PR #95 R1-1）。「古い」の印は取り直しに**成功したとき**だけ下ろす（R2-1）
- `npm run lint` の `@wordpress/no-unused-vars-before-return` は、早期 return より前に**関数呼び出し**で代入した変数を error にする。応答を待つ前に値を控えるなら `ref.current` のようなメンバー参照で読む（`activeRuns.selectionRef.current`。`platformGenerationRef.current` と同じ。PR #95）
- **翻訳する文字列の書き方**（R3-2）: 訳した文をつなぐときは `' '` を直に挟まず `joinSentences()`、語を並べるときは `join( ', ' )` でなく `joinList()` を使う（`src/i18n.ts`。日本語訳で「。 」「, 」が残る）。区切りだけの msgid（`', '`）は `@wordpress/i18n-no-flanking-whitespace` が lint で拒むので、`%1$s, %2$s` のような書式にする。件数＋複数形の名詞の文は `_n()`、日時・金額は `toLocaleString()`／`Intl.*( undefined )` でなく `displayLocale()`（WordPress のユーザーの言語。ブラウザの言語と食い違う）。**JS の文字列は `build/index.js` から抜く**（make-pot は TypeScript を読まない）ので、POT の参照は `src` ではなく `build/index.js:<行>` になる。文字列を変えたら `npm run i18n:pot` からやり直す（CLAUDE.md）。同じ英文を別の意味（店名とプラットフォーム ID など）で使うと make-pot が翻訳者コメントの食い違いを警告し、`i18n:check` が落ちる
